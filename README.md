# ALU Regex Data Extraction & Secure Validation

## Project Overview

This project is a regex-based data extraction and validation program developed for the **African Leadership University (ALU)** Regex Onboarding Hackathon.

The program processes raw, production-style text and uses regular expressions to identify structured information such as email addresses, URLs, phone numbers, credit card numbers, times, HTML tags, hashtags, and currency amounts.

Because input from external sources cannot automatically be trusted, the program also includes validation and security checks to reject or safely ignore malformed, suspicious, or potentially malicious data.

---

## Objectives

The program is designed to:

* Extract structured data from unstructured raw text.
* Validate extracted values using practical regular expressions.
* Handle realistic variations in formatting, spacing, punctuation, and data representation.
* Identify and reject malformed or suspicious input.
* Apply additional validation to ALU email addresses.
* Validate credit card numbers using the Luhn algorithm.
* Protect sensitive information by masking credit card numbers in the output.
* Produce structured JSON output that can be easily inspected and verified.

# Data Types Extracted

The program implements regex patterns for all eight available data categories.

## 1. Email Addresses

The program identifies properly formatted email addresses using a regular expression.

It also performs additional validation for ALU-specific email addresses.

### ALU Official Email

Valid addresses must end with:

```text
@alueducation.com
```

Example:

```text
student@alueducation.com
```

### ALU Alumni Email

Valid addresses must end with:

```text
@alumni.alueducation.com
```

Example:

```text
graduate@alumni.alueducation.com
```

### ALU SI Email

Valid addresses must end with:

```text
@si.alueducation.com
```

Example:

```text
student@si.alueducation.com
```

The validation also ensures that the email has a valid local part and does not contain malformed structures such as multiple `@` symbols or invalid domain formatting.

---

## 2. URLs

The program extracts URLs from the raw text and validates their structure.

Examples include:

```text
https://www.example.com
http://example.org/page
https://example.com/search?q=student
```

The program also checks URLs for suspicious schemes or patterns before treating them as safe extracted data.

---

## 3. Phone Numbers

The program identifies phone numbers in different realistic formats.

Examples include:

```text
+250 788 123 456
+1 (202) 555-0198
+44 20 7946 0958
+49 30 123456
```

The regex allows common differences in spacing, parentheses, hyphens, and international dialing formats.

---

## 4. Credit Card Numbers

The program identifies possible credit card numbers while allowing common formatting variations such as spaces and hyphens.

Examples of formats that may appear in raw text include:

```text
4111 1111 1111 1111
4111-1111-1111-1111
```

After extraction, the number is validated using the **Luhn algorithm** to reduce false positives.

For security reasons, complete credit card numbers are not displayed in the final output. Instead, sensitive digits are masked so that only limited information, such as the final four digits, remains visible.

Example:

```text
************1111
```

The validation helps distinguish realistic times from invalid values.

# Security Considerations

Input received from an external API or another untrusted source should never automatically be considered safe.

This project therefore applies several defensive techniques.

## Input Sanitization

The program processes the raw text before extraction and accounts for unusual or unwanted characters.

This helps reduce problems caused by malformed input and control characters.

## Suspicious Input

The program checks for patterns that may indicate injection attempts or dangerous content.

Suspicious content is rejected, ignored, or classified rather than being blindly processed as trustworthy data.

## URL Security

Extracted URLs are checked before being accepted as safe values.

Potentially dangerous URL schemes or suspicious patterns are not treated as normal URLs.

## HTML Security

HTML tags are extracted separately from their security classification.

This is important because an HTML tag appearing in text should not automatically be interpreted as safe content.

## Credit Card Protection

Credit card numbers are sensitive information.

The program therefore:

1. Extracts possible card numbers.
2. Removes formatting characters for validation.
3. Checks the number using the Luhn algorithm.
4. Masks sensitive digits before including the value in the output.

This prevents unnecessary exposure of complete card numbers.

## No Dynamic Code Execution

The program does not use functions such as:

```text
eval()
exec()
```

Extracted text is treated as data and is not executed as Python code.

# Validation Approach

The program follows a general extraction and validation process:

```text
Raw Text
   ↓
Input Sanitization
   ↓
Regex Extraction
   ↓
Candidate Validation
   ↓
Security Checks
   ↓
Sensitive Data Masking
   ↓
Structured JSON Output
```

The important principle is that **matching a regex does not automatically mean that the extracted value is trustworthy**.

For this reason, the program uses additional validation where necessary.

For example:

* Emails are checked for valid structure.
* ALU emails are checked against the required ALU domains.
* Credit cards are checked using the Luhn algorithm.
* URLs are checked for suspicious schemes.
* Potentially dangerous HTML is classified.
* Sensitive information is masked before output.

# Limitations

Regular expressions are useful for identifying structured patterns, but they cannot guarantee that every extracted value is genuinely real or usable.

For example:

* A syntactically valid email address may not actually exist.
* A URL may have a valid structure but the website may not exist.
* A phone number may have a valid format but may not be assigned.
* A credit card number may pass the Luhn check without being an active card.
* HTML detection using regex is not a replacement for a full HTML parser.

Therefore, this project focuses on **regex-based extraction and defensive validation**, as required by the assignment.
